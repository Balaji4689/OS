01 — Foundations

What is an Operating System?

System software that acts as an interface between the user and computer hardware — managing all resources so programs can run.

Definition & Role
  • An OS manages CPU, memory, storage, input/output, and security
  • Acts as an interface between user applications and hardware
  • Without an OS, every program would have to directly manage hardware — impossible for modern software
  • Examples: Windows, macOS, Linux, Android, iOS

Functions of an OS

🔲 Process Management
  • Creates, schedules, and terminates processes
  • Manages CPU time fairly among all running programs
🧠 Memory Management
  • Allocates and frees RAM for processes
  • Manages virtual memory and paging
💾 Storage Management
  • Manages file systems and disk access
  • Handles read/write operations
⌨️ I/O Management
  • Controls communication with devices
  • Uses device drivers as translators
🔒 Security & Protection
  • User authentication and access control
  • Protects processes from each other
🌐 Networking
  • Manages network connections and protocols
  • Enables inter-process communication (IPC)

Types of Operating Systems

  • Batch OS — processes jobs in batches without user interaction; old mainframes
  • Time-Sharing OS — multiple users share CPU simultaneously (Unix)
  • Real-Time OS (RTOS) — guaranteed response within a deadline (air traffic control, medical devices)
  • Distributed OS — manages a group of networked computers as one system
  • Embedded OS — runs on specific hardware (routers, washing machines)
  • Mobile OS — optimised for mobile devices (Android, iOS)
02 — Kernel

Kernel

The central core of the OS — controls CPU, memory, devices, and process management. Runs in privileged mode (kernel space).

💡 The kernel is the bridge between software and hardware. User programs run in "user space"; the kernel runs in "kernel space" with full hardware access.
Monolithic Kernel Linux, Unix
  • All OS services run in a single large kernel in kernel space
  • Very fast — no communication overhead between components
  • Hard to maintain — a bug in one module can crash the whole system
  • Examples: Linux, older Unix
Microkernel Minix, QNX
  • Only essential services (CPU scheduling, memory, IPC) run in kernel space
  • Other services run in user space
  • More stable and secure — a crash in one service doesn't kill the kernel
  • Slower due to frequent user↔kernel communication
  • Examples: Minix, QNX, HURD
Hybrid Kernel Windows, macOS
  • Combination of monolithic and microkernel
  • Core services in kernel space; others can run in user space
  • Balance of speed and stability
  • Examples: Windows NT, macOS (XNU)
Nano / Exo Kernel
  • Exokernel: minimal — just multiplexes hardware; OS policies in user space
  • Nanokernel: even more minimal than microkernel
  • Used in research operating systems
Kernel TypeSpeedStabilityExamples
MonolithicFastLower (one bug can crash)Linux, Unix
MicrokernelSlowerHigh (isolated services)Minix, QNX

03 — Concurrency Types

Multiprocessing, Multithreading, Multiprogramming & Multitasking

Four key OS concepts about how a system runs multiple tasks — very commonly confused in interviews.

Multiprocessing multiple CPUs
  • More than one CPU / core works at the same time
  • True parallelism — tasks run literally simultaneously
  • Example: 4-core laptop — one core plays music, another runs Chrome, another runs a game
Multithreading one process, many threads
  • One program does many things at the same time using threads
  • Threads share the same memory space of a process
  • Example: WhatsApp — one thread sends messages, one receives, one shows notifications
Multiprogramming CPU never idle
  • CPU switches between programs when one is waiting (e.g. for I/O)
  • Keeps CPU busy — no wasted idle time
  • Single CPU, no time-slicing — process runs until it blocks
  • Example: Program A waits for internet → CPU immediately works on Program B
Multitasking rapid switching
  • One CPU does many tasks by fast switching between them (time slicing)
  • Appears simultaneous to the user
  • Extension of multiprogramming with time-sharing
  • Example: You watch YouTube + chat on WhatsApp + download a file at the same time

04 — Interface Types

CLI vs GUI

Two ways users interact with an operating system.

CLI — Command Line Interface developer-preferred
  • Text-based — user types commands
  • Faster for experienced users; more powerful and scriptable
  • Uses less system resources (no graphics rendering)
  • Examples: Linux terminal, Windows Command Prompt, PowerShell
  • Common commands: ls, cd, mkdir, rm, grep
GUI — Graphical User Interface user-friendly
  • Icons, windows, and mouse-driven — easy to use
  • Visual and intuitive; no commands to memorise
  • Uses more system resources (graphics, rendering)
  • Examples: Windows Desktop, macOS, GNOME on Linux
05 — System Calls

System Calls

A request made by a user-space program to the OS kernel to perform a privileged task like reading a file or creating a process.

💡 User programs cannot directly access hardware. They request the OS via system calls — the OS kernel then performs the action on their behalf.
Types of System Calls
  • Process control: fork(), exec(), exit(), wait()
  • File management: open(), read(), write(), close()
  • Device management: ioctl(), read(), write()
  • Information maintenance: getpid(), alarm(), sleep()
  • Communication: pipe(), socket(), send(), recv()
Key System Calls — Details
  • fork() — creates a new child process (exact copy of parent)
  • exec() — replaces the current process image with a new program
  • read() — reads data from a file or device
  • write() — writes data to a file or device
  • exit() — terminates a process and returns status to parent
  • wait() — parent waits for child process to finish

07 — System Structure NEW

User Mode vs Kernel Mode

CPUs operate in two privilege levels to protect the OS from user programs. This hardware-enforced boundary is fundamental to OS security.

💡 The CPU has a hardware bit (privilege bit) that determines whether it's in kernel mode or user mode. Every modern OS uses this to protect critical operations.
User Mode restricted
  • Normal programs (your apps, browser, games) run here
  • Limited access — cannot directly touch hardware or kernel memory
  • Cannot execute privileged instructions (e.g. directly modify CPU registers)
  • If a user program crashes, only that process dies — OS is safe
  • To do anything privileged, must make a system call to switch to kernel mode
Kernel Mode privileged
  • The OS kernel runs here — full hardware access
  • Can execute any CPU instruction, access any memory address
  • Manages hardware, handles interrupts, runs device drivers
  • A bug in kernel mode can crash the entire system (Blue Screen of Death)
  • Entry points: system calls, hardware interrupts, software exceptions

08 — Interrupts & Booting NEW

Interrupts & Booting Process

Interrupts let hardware signal the CPU asynchronously. Booting is the step-by-step process the system follows from power-on to a usable OS.

Interrupts frequently asked
  • A signal to the CPU that an event needs immediate attention — pauses the current task
  • CPU saves its current state, executes the Interrupt Service Routine (ISR), then resumes
  • Hardware Interrupts: generated by hardware devices (keyboard press, mouse click, disk I/O complete, timer)
  • Software Interrupts (Traps): triggered by a program — used for system calls (INT 0x80 on x86 Linux)
  • Exception: caused by a CPU error — e.g. division by zero, invalid memory access (page fault)
  • The Interrupt Vector Table (IVT) maps interrupt numbers to their handler addresses
Maskable vs Non-Maskable Interrupts
  • Maskable: can be temporarily disabled by the CPU (e.g. during a critical section)
  • Non-Maskable (NMI): cannot be ignored — used for catastrophic hardware failures (memory error, power failure)
Interrupt Handling Steps
  • 1. Hardware raises interrupt signal
  • 2. CPU finishes current instruction
  • 3. CPU saves program counter & registers
  • 4. CPU looks up ISR address in IVT
  • 5. ISR executes
  • 6. CPU restores state and resumes

Booting Steps — Explained
  • POST (Power-On Self Test): BIOS/UEFI checks if hardware (RAM, CPU, keyboard) is working
  • BIOS/UEFI: firmware stored on the motherboard; initialises hardware and finds bootable device
  • MBR (Master Boot Record): first 512 bytes of a bootable disk — contains bootloader code and partition table
  • UEFI + GPT: modern replacement for BIOS+MBR; supports larger disks and faster booting
  • Bootloader (GRUB): loads the OS kernel into memory
  • Kernel initialisation: kernel sets up drivers, mounts root filesystem
  • Init / systemd: first process (PID 1) — starts all system services and gets to login
09 — Process & Thread

Program vs Process vs Thread

Three fundamental concepts — know the exact difference between all three.

Program passive
  • A set of instructions stored on disk
  • Not running — just a file
  • Example: Chrome.exe sitting in your C: drive
Process active
  • A program in execution
  • Has its own memory space, CPU time, files
  • Each process is independent — crash of one doesn't affect others
  • Example: Chrome.exe running with multiple tabs
Thread lightweight
  • The smallest unit of execution within a process
  • Shares the process's memory and resources
  • Lighter than processes — faster to create and switch
  • Example: Each browser tab may use a separate thread

10 — PCB & Process States

Process Control Block & Process States

The OS uses a PCB to track every process, and every process moves through defined states during its lifetime.

PCB — Process Control Block frequently asked
  • A data structure the OS maintains for every running process
  • Process ID (PID) — unique number identifying the process
  • Process State — current state: New, Ready, Running, Waiting, Terminated
  • Program Counter (PC) — address of the next instruction to execute
  • CPU Registers — saved register values (used during context switching)
  • Memory Info — memory limits, page table base address
  • I/O Status — list of open files and I/O devices
  • Scheduling Info — priority, scheduling queue pointers

11 — CPU Scheduling

CPU Scheduling

How the OS decides which process gets the CPU next — one of the most tested OS topics.

Why CPU Scheduling is Needed
  • Multiple processes compete for one CPU — scheduling ensures fair and efficient allocation
  • Maximises CPU utilisation, throughput, and minimises waiting time
Preemptive Scheduling can interrupt
  • OS can stop a running process and give CPU to another
  • Better for interactive systems
  • Examples: Round Robin, Priority (preemptive), SRTF
Non-Preemptive Scheduling runs to completion
  • Once a process gets CPU, it runs until it finishes or blocks
  • Simpler but less responsive
  • Examples: FCFS, SJF (non-preemptive), Priority (non-preemptive)

12 — Scheduling Algorithms

CPU Scheduling Algorithms

Specific methods used to decide which process runs next — know all types with their advantages and disadvantages.

1. FCFS — First Come First Serve non-preemptive
  • Processes are executed in the order they arrive
  • Simple to implement using a FIFO queue
  • Problem: Convoy Effect — a long process blocks all shorter ones behind it
  • Poor average waiting time if a long process arrives first
2. SJF — Shortest Job First optimal average wait
  • Process with the smallest burst time is executed first
  • Gives minimum average waiting time — optimal among non-preemptive algorithms
  • Problem: Starvation — long processes may wait forever if short ones keep coming
  • SRTF (Shortest Remaining Time First) = preemptive version of SJF
3. Priority Scheduling
  • Each process has a priority number; highest priority executes first
  • Can be preemptive or non-preemptive
  • Problem: Starvation — low-priority processes may never run
  • Solution: Aging — gradually increase priority of waiting processes over time
4. Round Robin (RR) most common for time-sharing
  • Each process gets a fixed time slice called a time quantum
  • After quantum expires, process is moved to the back of the ready queue
  • Fair — no starvation; best for interactive systems
  • Performance depends on quantum size: too small = too many context switches; too large = behaves like FCFS
5. Multilevel Queue (MLQ)
  • Processes are divided into separate queues (e.g. system, interactive, batch)
  • Each queue has its own scheduling algorithm
  • Processes cannot move between queues
6. Multilevel Feedback Queue (MLFQ) most flexible
  • Like MLQ but processes can move between queues based on behaviour
  • CPU-intensive processes get lower priority over time; I/O-bound get higher
  • Most complex but most flexible and widely used in practice (e.g. Linux)

14 — Multithreading

Multithreading & Thread Models

Running multiple threads at the same time within a single process for faster execution and better CPU utilisation.

Benefits of Multithreading
  • Better CPU utilisation — while one thread waits for I/O, another can run
  • Faster execution — tasks run concurrently
  • Improved responsiveness — UI stays responsive even during heavy work
  • Resource sharing — threads share memory, no IPC overhead
  • Lower cost than creating new processes

Types of Threads

User-Level Threads (ULT)
  • Managed by the application (user-space library)
  • OS is not aware of them
  • Fast to create and switch — no kernel involvement
  • Problem: if one thread blocks, all threads block
Kernel-Level Threads (KLT)
  • Managed by the OS kernel
  • OS can schedule threads on different CPUs
  • Slower to create — kernel involvement overhead
  • If one thread blocks, others can still run

Multithreading Models

Many-to-One
  • Many user threads → one kernel thread
  • If one blocks → all block
  • Cannot run in true parallel
One-to-One Windows, Linux
  • Each user thread → one kernel thread
  • True parallelism on multi-core CPUs
  • More overhead to create
Many-to-Many
  • Many user threads mapped to many kernel threads
  • Flexible and efficient
  • Best of both worlds
15 — Thread Operations NEW

Thread Creation, Synchronization & Pools

Practical thread operations — how threads are created and managed in real systems including Java, Node.js, and thread pools.

Thread Creation
  • A new thread is created within a process — it gets its own stack and registers but shares heap/code
  • Creation is cheaper than forking a process (no new memory space needed)
  • Each thread has: Thread ID, Stack, Program Counter, Register set
  • Threads are terminated with join() — parent waits for child thread to finish
Thread Pools production pattern
  • A pre-created set of worker threads waiting for tasks
  • Avoids overhead of creating/destroying threads for every request
  • Tasks are submitted to a queue; idle threads pick them up
  • Used heavily in web servers (Tomcat, Node.js worker threads, Java ExecutorService)
  • Pool size tuning: too few = slow; too many = memory waste + context switch overhead

Java Threads

  • Java threads are kernel-level threads mapped 1:1 to OS threads
  • Create by extending Thread class or implementing Runnable interface
  • start() — creates new thread and calls run() in it
  • join() — current thread waits until the target thread finishes
  • synchronized keyword — built-in monitor; only one thread enters the block at a time
  • ExecutorService — Java's thread pool API (Executors.newFixedThreadPool(n))
  • volatile — ensures a variable's value is always read from main memory (not CPU cache)

Node.js Event Loop & Worker Threads

  • Node.js is single-threaded but non-blocking — uses an event loop for concurrency
  • Event Loop: continuously polls for I/O completions, timers, and callbacks — executes them one at a time
  • I/O operations (file, network) are offloaded to the OS via libuv thread pool (default 4 threads)
  • CPU-bound tasks block the event loop — solution: Worker Threads (Node.js v10.5+)
  • worker_threads module creates true OS threads for CPU-intensive work
  • Cluster module: spawns multiple Node.js processes (one per CPU core) to scale across cores
💡 Node.js concurrency model: One thread + event loop + async I/O = handles thousands of requests. For CPU work, use Worker Threads. For scaling across cores, use Cluster.
16 — Process Synchronization

Process Synchronization

Ensuring multiple processes/threads work together correctly when sharing resources — prevents race conditions and data corruption.

Race Condition must know
  • Occurs when two or more processes access shared data simultaneously and the result depends on execution order
  • Example: two threads both read balance = 1000, both add 500, both write back 1500 — instead of correct 2000
  • Solved by synchronization mechanisms: Mutex, Semaphore, Monitor
17 — Critical Section

Critical Section Problem

A part of the program where shared resources are accessed — must be protected so only one process enters at a time.

Requirements for a Valid Solution all 3 must hold
  • Mutual Exclusion — only one process can be in the critical section at a time
  • Progress — if no process is in the critical section, one of the waiting processes should be allowed in without indefinite delay
  • Bounded Waiting — there is a limit on how many times other processes can enter the critical section before a waiting process gets its turn (no starvation)
Structure of a Process with Critical Section
Entry Section → Critical Section → Exit Section → Remainder Section
18 — Synchronization Tools

Mutex, Semaphore & Monitor

The three main tools used to solve the critical section problem and manage shared resources.

Mutex lock/unlock
  • Mutual Exclusion lock — binary: locked or unlocked
  • Only the process that locked it can unlock it
  • Used when only one thread at a time should access a resource
  • Operations: lock() and unlock()
  • Example: protecting a bank balance from simultaneous updates
Semaphore counter-based
  • An integer variable that controls access — can be > 1
  • Operations: wait() (decrement) and signal() (increment)
  • Binary Semaphore: 0 or 1 — works like a mutex
  • Counting Semaphore: allows N processes — e.g. 3 database connections allowed
  • Can be released by a different process (unlike mutex)
Monitor high-level
  • A high-level synchronization construct built into OOP languages
  • Only one process can be active inside the monitor at a time
  • Uses condition variables (wait() and signal()) for coordination
  • Examples: Java synchronized keyword, Python with lock:

19 — Spinlock & Atomics NEW

Spinlock, Atomic Operations & Lock-Free Programming

Low-level synchronization primitives used in OS kernels and high-performance systems where sleeping is too expensive.

Spinlock busy-wait
  • A lock where a thread continuously loops (spins) checking if the lock is free
  • Does NOT put the thread to sleep — wastes CPU cycles but avoids context switch overhead
  • Best when: lock is held for a very short time (microseconds)
  • Bad when: lock is held long — CPU burned on useless spinning
  • Used inside OS kernels (e.g. Linux kernel spinlocks) and interrupt handlers
  • Key operations: spin_lock(), spin_unlock()
Spinlock vs Mutex
  • Mutex: thread sleeps if lock unavailable → context switch → wake up later
  • Spinlock: thread keeps running and retrying → no context switch
  • Mutex better for long critical sections; Spinlock better for very short ones
  • Spinlocks work on single-core systems only if interrupts are disabled
Atomic Operations hardware-guaranteed
  • Operations that complete entirely or not at all — cannot be interrupted mid-way
  • Hardware provides atomic instructions: test-and-set, compare-and-swap (CAS), fetch-and-add
  • CAS(addr, expected, new): if *addr == expected, write new and return true — all in one uninterruptible step
  • Foundation of all lock-free and wait-free data structures
  • Java: AtomicInteger.incrementAndGet(), AtomicReference.compareAndSet()
  • C++: std::atomic<int>
Lock-Free Programming
  • Design data structures that multiple threads can use without traditional locks
  • Uses atomic operations (CAS) to ensure correctness without mutexes
  • Lock-free: at least one thread always makes progress (no global blocking)
  • Wait-free: every thread makes progress in bounded steps (stronger guarantee)
  • Examples: lock-free queues, stacks (used in Java's ConcurrentLinkedQueue)
  • Benefits: no deadlock, no priority inversion; Cons: complex to implement correctly
20 — Classical Sync Problems NEW

Classical Synchronization Problems

Famous problems used to test and demonstrate synchronization solutions — almost guaranteed to appear in interviews.

1. Producer-Consumer Problem bounded buffer
  • Setup: Producer generates data and puts it in a shared buffer; Consumer takes it out
  • Problems: Producer should wait if buffer is full; Consumer should wait if buffer is empty; both shouldn't access buffer at same time
  • Solution: Use 3 semaphores — mutex (mutual exclusion), full (count of full slots), empty (count of empty slots)
  • Producer: wait(empty) → wait(mutex) → add item → signal(mutex) → signal(full)
  • Consumer: wait(full) → wait(mutex) → remove item → signal(mutex) → signal(empty)
  • Real examples: CPU and disk I/O, message queues, print spooler
2. Readers-Writers Problem
  • Setup: Multiple readers can read simultaneously; writers need exclusive access
  • Rules: Multiple readers allowed at once; writer must wait for all readers to finish; readers must wait if writer is writing
  • First Readers-Writers: readers have priority — writers may starve
  • Second Readers-Writers: writers have priority — readers may starve
  • Solution: semaphore rw_mutex for writer exclusion, mutex for read count, integer read_count
  • Real examples: database systems, shared file access, web caches
3. Dining Philosophers Problem deadlock showcase
  • Setup: 5 philosophers sit at a round table; each needs 2 forks to eat; one fork between each pair
  • Problem: if all pick up left fork simultaneously → deadlock (circular wait)
  • Solutions:
  • Allow only 4 philosophers at table at once (breaks circular wait)
  • Odd philosophers pick left first; even pick right first (breaks symmetry)
  • Pick up both forks atomically — only if both available
  • Use a waiter/arbitrator who grants permission to pick up forks
  • Demonstrates all 4 deadlock conditions and how to break them
4. Sleeping Barber Problem
  • Setup: A barber shop with one barber, one barber chair, and N waiting chairs
  • If no customers: barber sleeps in chair. Customer arrives: if barber sleeping → wake him; if waiting chairs free → sit and wait; if all chairs full → leave
  • Problem: race condition between checking if barber asleep and sitting down
  • Solution: semaphores customers (waiting count), barbers (idle barbers), mutex (protect shared state)
  • Real analogy: thread pool — sleeping threads = idle workers; customers = incoming tasks
21 — Deadlock

Deadlock

A situation where two or more processes are permanently stuck, each waiting for resources held by the others.

💡 Classic example: T1 holds Resource A and waits for B. T2 holds Resource B and waits for A. Neither can proceed — deadlock!

4 Necessary Conditions (all must hold for deadlock)

1. Mutual Exclusion
  • Only one process can use a resource at a time
  • Resources are non-shareable (e.g. printer)
2. Hold and Wait
  • A process holds at least one resource and waits to acquire more
3. No Preemption
  • Resources cannot be forcibly taken from a process
  • A process must voluntarily release its resources
4. Circular Wait
  • A circular chain of processes — each waits for a resource held by the next
  • P1 waits for P2, P2 waits for P3, P3 waits for P1

Deadlock Handling Methods

Prevention
  • Eliminate at least one of the 4 conditions from happening
  • Example: require all resources to be requested at once (eliminates Hold & Wait)
  • Conservative — may waste resources
Avoidance Banker's Algorithm
  • OS checks if granting a resource leaves the system in a safe state
  • If safe → grant. If unsafe → make process wait
  • Uses Banker's Algorithm
Detection
  • Allow deadlock to occur; detect it using a wait-for graph
  • Periodically check for cycles in the resource allocation graph
Recovery
  • After detection: kill one or more processes to break the deadlock
  • Or: preempt resources from one process and give to another
  • Rollback: restart a process to a safe checkpoint
22 — Banker's Algorithm

Banker's Algorithm & Wait-For Graph

The classic deadlock avoidance algorithm — checks if resource allocation will lead to a safe state before granting.

Banker's Algorithm frequently asked
  • Named because a bank never allocates cash that might cause it to run out of money
  • Before granting a resource, OS checks if the system will be in a safe state
  • Safe state: there exists a sequence of processes where each can finish using currently available resources
  • Data structures used: Available (free resources), Max (max each process needs), Allocation (currently allocated), Need = Max − Allocation
  • If granting the request keeps the system in a safe state → grant; otherwise → wait
Wait-For Graph
  • A directed graph where nodes represent processes
  • An edge P1 → P2 means P1 is waiting for a resource held by P2
  • A cycle in the graph = deadlock detected
  • Used for deadlock detection in systems with single instances of each resource type
23 — Memory Management

Memory Management

The OS job of allocating, tracking, and freeing memory so programs can run efficiently.

Cache Memory fastest
  • Very small, very fast memory inside or near the CPU
  • Stores frequently used data to speed up CPU access
  • L1 (fastest/smallest) → L2 → L3 (larger/slower)
Main Memory (RAM)
  • Temporary memory storing currently running programs
  • CPU accesses it directly — much faster than disk
  • Volatile — lost when power is off
Secondary Storage
  • Permanent memory (HDD, SSD) for long-term storage
  • Data persists when power is off
  • Much slower than RAM
Logical Address CPU-generated
  • Address generated by the CPU when a process accesses memory
  • Also called virtual address — what the program sees
  • Does not correspond directly to physical RAM location
Physical Address actual RAM
  • Actual address in physical RAM where data is stored
  • The MMU translates logical → physical at runtime
MMU — Memory Management Unit
  • Hardware unit that translates logical addresses to physical addresses at runtime
  • Every memory access by a process goes through the MMU
  • Works using the process's page table
  • Also enforces memory protection — prevents one process from accessing another's memory
24 — Address Binding NEW

Address Binding

The process of mapping a program's symbolic addresses to actual memory addresses — happens at different stages of program execution.

What is Address Binding?
  • A program uses symbolic names (variable names, function names) that must be converted to memory addresses
  • This conversion (binding) can happen at different times — compile, load, or runtime
Compile-Time Binding
  • Addresses are fixed at compile time
  • If the program must always load at address X, the compiler generates absolute addresses
  • Very inflexible — program must always be loaded at same location
  • Example: old DOS programs (COM files)
Load-Time Binding
  • Addresses resolved when the program is loaded into memory
  • Compiler generates relocatable code; loader converts to absolute addresses
  • More flexible than compile-time but still fixed once loaded
  • Must reload to move in memory
Runtime Binding modern OS
  • Addresses translated during execution by the MMU
  • Process can be moved in memory while running
  • Requires hardware support (MMU + relocation register)
  • Used by all modern OSes (enables virtual memory)
💡 Modern OSes use runtime binding. The CPU generates a logical address; the MMU adds the base register value to get the physical address — every single memory access, in hardware, at full speed.
25 — Memory Allocation

Free Space Management & Allocation Strategies

How the OS decides where in RAM to place each process.

Contiguous Allocation

Fixed Partitioning
  • Memory divided into fixed-size partitions at boot time
  • Simple but causes internal fragmentation (wasted space within partition)
Dynamic Partitioning
  • Partitions created as needed based on process size
  • Causes external fragmentation (free holes scattered in memory)
  • Solution: compaction (move processes to consolidate free space)

Allocation Strategies

First Fit
  • Allocates the first free block that is big enough
  • Fast; may leave small unusable holes at the front
Next Fit
  • Like First Fit but starts searching from the last allocated position
  • Spreads allocation more evenly
Best Fit
  • Allocates the smallest free block that can hold the process
  • Minimises wasted space per allocation; leaves many tiny unusable fragments
Worst Fit
  • Allocates the largest free block
  • Leaves large leftover holes that may be usable for future processes
⚠ Internal fragmentation: wasted space inside an allocated block (block too big for process). External fragmentation: enough total free space exists but it's scattered in non-contiguous holes.
26 — Paging & Segmentation

Paging & Segmentation

Non-contiguous memory allocation techniques that eliminate external fragmentation.

Paging most common
  • Divides logical memory into fixed-size pages; physical memory into fixed-size frames
  • A page table maps each page number → frame number in RAM
  • Eliminates external fragmentation; may have small internal fragmentation in the last page
  • Page size is a power of 2 (e.g. 4 KB)
  • Logical address = (Page Number | Offset); translated to (Frame Number | Offset)
Segmentation
  • Divides a program into logical segments of variable sizes (code, stack, heap, data)
  • More meaningful than paging — reflects programmer's view of memory
  • A segment table stores base address and limit (size) of each segment
  • Eliminates internal fragmentation; may have external fragmentation
  • Many modern OSes use segmentation + paging combined

27 — Virtual Memory

Virtual Memory & Demand Paging

Allows programs larger than RAM to run by using disk space as an extension of RAM.

Virtual Memory
  • Creates an illusion of large memory by using secondary storage (disk) as extra RAM
  • Only the needed pages stay in RAM; the rest stay on disk (swap space)
  • Programs don't need to know the physical memory layout
✅ Advantages
  • Programs larger than RAM can run
  • Better memory utilisation — only active pages in RAM
  • More processes can be in memory simultaneously
  • Process isolation improved
❌ Disadvantages
  • Slower than pure RAM (disk access)
  • Page faults reduce performance
  • Complex OS implementation
  • Risk of thrashing under heavy load
Demand Paging
  • Loads a page into RAM only when it is needed (on demand)
  • Pages not accessed stay on disk — saves memory
  • If a needed page is not in RAM → page fault occurs → OS loads it from disk
Page Fault
  • Occurs when a program accesses a page not currently in RAM
  • Process: CPU generates page fault interrupt → OS finds the page on disk → loads it into a free frame → updates page table → resumes process
  • Frequent page faults = very slow performance (leads to thrashing)
28 — Page Replacement

Page Replacement Algorithms

When RAM is full and a new page is needed, the OS must decide which existing page to remove — these algorithms decide which.

FIFO — First In First Out
  • Removes the page that has been in memory the longest
  • Simple to implement
  • Problem: Belady's Anomaly — adding more frames can increase page faults
Optimal Page Replacement best theoretical
  • Removes the page that will not be used for the longest time in the future
  • Gives the minimum possible page faults
  • Not implementable in practice — requires future knowledge; used as a benchmark
LRU — Least Recently Used most used in practice
  • Removes the page that was least recently used
  • Based on the principle that recently used pages will be used again soon
  • Good performance; requires tracking access time (stack or counter implementation)
LFU — Least Frequently Used
  • Removes the page with the lowest access count
  • Pages used rarely are removed first
MFU — Most Frequently Used
  • Removes the page with the highest access count
  • Based on idea that heavily used pages have done their job
  • Rarely used in practice
Clock (Second Chance) Algorithm practical LRU approximation NEW
  • An efficient approximation of LRU — used by Linux and many real OSes
  • Each page has a reference bit (R): set to 1 when page is accessed, 0 when not
  • A clock hand sweeps through frames in circular order
  • If R=1: give it a second chance — set R=0 and move to next frame
  • If R=0: this page hasn't been used recently → replace it
  • Much cheaper than tracking full LRU order; only one bit per page

29 — Thrashing & TLB

Thrashing, TLB & Page Table

Performance-critical OS concepts — thrashing destroys performance; TLB speeds up address translation.

Thrashing performance killer
  • System spends more time swapping pages in and out than doing actual work
  • CPU utilisation drops drastically despite high system activity
  • Causes: too many processes in memory, very few frames per process, high page fault rate
  • Solution: working set model — keep the set of actively used pages in memory; reduce degree of multiprogramming
TLB — Translation Lookaside Buffer speed booster
  • A small, very fast cache inside the CPU that stores recent virtual → physical address mappings
  • Without TLB: every memory access requires two memory lookups (page table + data)
  • With TLB hit: direct physical address found — only one memory access needed
  • TLB hit: address found in TLB (fast). TLB miss: must consult page table (slow)
  • TLB is flushed on context switch (or use ASIDs to avoid flushing)
30 — I/O Management

I/O Management, Buffering & Spooling

How the OS manages communication with devices, and techniques to improve I/O performance.

I/O Buffering
  • Uses a temporary memory area (buffer) to store data while it transfers between device and program
  • Helps smooth out speed differences between CPU and I/O devices
  • Single Buffering: one buffer; device fills while CPU waits, then CPU processes
  • Double Buffering: two buffers; device fills one while CPU processes the other simultaneously — better throughput
Spooling (Simultaneous Peripheral Operations On-Line)
  • Stores I/O data on disk so multiple programs can share one device
  • Example: print spooling — multiple programs submit print jobs; printer processes them one by one from the spool queue
  • Allows programs to continue running without waiting for the device to be free
Device Drivers
  • Software that acts as a translator between the OS and specific hardware devices
  • OS sends generic commands; driver translates them to device-specific instructions
  • Each device (printer, GPU, keyboard) has its own driver
31 — I/O Hardware & DMA NEW

I/O Hardware, Polling, Interrupts & DMA

How the CPU actually communicates with hardware devices — three techniques with very different performance characteristics.

Device Controllers
  • Hardware components that manage communication between CPU and peripheral devices
  • Each controller has registers (status, control, data) that the CPU reads/writes
  • CPU sends commands by writing to controller registers; reads status to check completion
  • Examples: disk controller, USB controller, network interface card (NIC)
Polling (Busy-Wait I/O) CPU wasteful
  • CPU continuously checks the device status register in a loop
  • Simple to implement; works for fast devices
  • Wastes CPU cycles — CPU cannot do other work while waiting
  • Example: while(device.busy) { /* spin */ }
  • OK for very fast devices (microseconds); terrible for slow ones
Interrupt-Driven I/O efficient
  • CPU starts I/O operation, then goes back to doing useful work
  • Device raises an interrupt when it finishes
  • CPU handles the interrupt via ISR, then resumes normal work
  • Much better CPU utilisation than polling
  • Overhead: interrupt handling, context save/restore for each I/O
DMA — Direct Memory Access best for bulk
  • A special DMA controller transfers data directly between device and memory without CPU involvement
  • CPU programs the DMA (source, destination, size), then goes to other work
  • DMA does the transfer; raises interrupt when done
  • Best for large data transfers (disk reads, network packets, video)
  • CPU only involved at start and end — not during transfer

32 — Disk Scheduling

Disk Scheduling Algorithms

Decides which disk I/O request to serve first — goal is to minimise seek time (time for disk head to move to the right track).

FCFS — First Come First Serve
  • Requests served in the order they arrive
  • Simple and fair; no starvation
  • May result in lots of unnecessary head movement
SSTF — Shortest Seek Time First greedy
  • Serves the request closest to the current head position first
  • Reduces average seek time compared to FCFS
  • Problem: starvation of requests far from current head position
SCAN — Elevator Algorithm most practical
  • Disk head moves in one direction serving all requests; then reverses and serves in the other direction
  • Like an elevator — goes up serving floors, then goes down
  • No starvation; good performance
C-SCAN — Circular SCAN
  • Like SCAN but after reaching the end, head jumps back to the beginning without serving on the return
  • More uniform wait times than SCAN
  • Treats disk as a circular list of cylinders
LOOK NEW
  • Like SCAN but head only goes as far as the last request in each direction — doesn't go to disk end
  • More efficient than SCAN — avoids unnecessary travel to disk boundaries
  • Still reverses direction at last request
C-LOOK NEW
  • Like C-SCAN but head only goes to the last request (not disk end) before jumping back
  • Most efficient of all SCAN variants
  • Uniform wait times + no wasted travel

33 — RAID NEW

RAID — Redundant Array of Independent Disks

Combines multiple physical disks into one logical unit for improved performance, redundancy, or both. Crucial for production systems.

💡 RAID trades disk capacity for speed and/or fault tolerance. Know RAID 0, 1, and 5 — these are the most commonly asked in interviews.
RAID 0 — Striping speed only
  • Data is split (striped) across 2+ disks in blocks
  • Reads and writes happen in parallel → double the speed
  • No redundancy — if one disk fails, all data is lost
  • Min disks: 2. Usable capacity: 100% of total
  • Use case: video editing, scratch disks, where speed matters > safety
RAID 1 — Mirroring safety only
  • Data is mirrored identically on 2+ disks
  • If one disk fails, data is still on the other — full redundancy
  • Read performance improved (can read from either disk)
  • Write speed same (must write to all disks)
  • Min disks: 2. Usable capacity: 50% (1 disk wasted for mirror)
  • Use case: OS drives, critical data that cannot be lost
RAID 5 — Striping + Parity balanced
  • Data striped across disks + parity info distributed across all disks
  • Can recover from one disk failure using parity
  • Good read performance; write slightly slower (parity calculation)
  • Min disks: 3. Usable capacity: (N−1)/N total (1 disk worth = parity)
  • Use case: most popular for servers — balance of speed, capacity, and fault tolerance

34 — File System

File System

How the OS organises, stores, and retrieves data on storage devices.

File System Concepts
  • File: named collection of data stored on disk
  • Directory: organises files in a hierarchical structure
  • File Attributes: name, type, size, location, creation/modification time, permissions
  • File Operations: create, open, read, write, seek, close, delete

File Allocation Methods

Contiguous Allocation
  • File occupies consecutive blocks on disk
  • Fast sequential access
  • External fragmentation; hard to grow files
Linked Allocation
  • Each block has a pointer to the next block
  • No external fragmentation; files can grow
  • Slow random access — must follow chain
Indexed Allocation Unix i-nodes
  • An index block holds pointers to all file blocks
  • Fast random access; no external fragmentation
  • Used in Unix/Linux (inodes)
Common File Systems
  • FAT32 — old Windows; max file size 4 GB; widely compatible
  • NTFS — modern Windows; supports permissions, journaling, large files
  • ext4 — standard Linux file system; journaling, efficient
  • APFS — Apple file system; optimised for SSDs
35 — Directory Structure NEW

Directory Structure

How the OS organises the namespace for files — evolved from simple flat structures to hierarchical trees.

Single-Level Directory
  • All files in a single directory — one folder for everyone
  • Simplest structure; easy to implement
  • Problem: naming conflicts — two users can't have a file with same name
  • Doesn't scale — used in early, simple systems
Two-Level Directory
  • Each user gets their own directory; master directory at top
  • Solves naming conflicts between users
  • Problem: users can't organise files into subdirectories
  • No sharing between users easily
Tree-Structured modern OSes
  • Directories can contain files and subdirectories — arbitrary depth
  • Absolute path: /home/user/docs/file.txt
  • Relative path: from current working directory
  • Used by all modern OSes (Linux, Windows, macOS)
Acyclic-Graph & General Graph Directories
  • Acyclic-Graph: allows shared subdirectories/files — multiple paths to same file (hard links/symlinks in Linux)
  • General Graph: allows cycles — very complex; requires garbage collection to find unreachable files
  • Linux uses tree structure + symbolic links (soft links point to a path) + hard links (point to same inode)
36 — Free Space Management NEW

Free Space Management

The OS must track which disk blocks are free so it can allocate them to new files. Different methods have different time/space tradeoffs.

Bit Vector (Bitmap)
  • One bit per disk block: 1 = free, 0 = allocated (or reversed)
  • Simple to implement; easy to find contiguous free blocks
  • Fast with bitwise operations — CPU can check 32/64 blocks at once
  • Requires extra space: 1 bit per block (e.g. 1 TB disk with 4 KB blocks = 32 MB bitmap)
  • Used by NTFS and ext4
Free List (Linked List)
  • All free blocks are linked together in a list
  • No wasted space — uses the free blocks themselves to store pointers
  • Finding a contiguous group of free blocks is slow — must traverse list
  • Used in some simple file systems
Grouping
  • First free block stores addresses of N free blocks; last of those stores N more, etc.
  • Can find large numbers of free blocks quickly
  • More efficient than simple linked list for bulk allocation
Counting
  • Stores (address, count) pairs: "block X is free, and the next 5 blocks after it are also free"
  • Efficient when free blocks tend to be contiguous (e.g. after file deletion)
  • Shorter list than bit vector when many contiguous free regions exist
37 — Concurrency & Multicore NEW

Concurrency, Race Conditions & Multicore Processing

Advanced concurrency concepts that matter for modern multi-core systems and parallel computing.

Race Condition — Deep Dive must know
  • A race condition is when the program output depends on the relative timing of concurrent operations
  • Root cause: non-atomic read-modify-write operations on shared data
  • Example: counter++ is 3 machine instructions (read, add, write) — interleaving causes incorrect results
  • Data race: specifically when two threads access same memory with no synchronization and at least one is a write
  • Prevention: atomics, mutexes, immutable data, message passing (no shared state)
Multicore Processing
  • Modern CPUs have multiple cores — each is an independent processor
  • Cores share L3 cache and RAM; each has private L1/L2
  • Cache coherence problem: if core 1 updates a variable, core 2's cache may have stale value
  • Hardware solves this with MESI protocol (Modified, Exclusive, Shared, Invalid)
  • False sharing: two variables in the same cache line accessed by different cores → performance killer
  • Hyper-threading: one physical core appears as 2 logical CPUs (shares execution units)
Parallel Computing
  • Data parallelism: same operation on different parts of data simultaneously (array addition)
  • Task parallelism: different tasks run on different processors at the same time
  • Amdahl's Law: speedup limited by the serial portion — if 20% can't be parallelised, max speedup = 5× regardless of cores
  • OpenMP: pragma-based parallelism for C/C++/Fortran
  • SIMD: Single Instruction Multiple Data — one instruction operates on multiple data points (GPU cores, AVX)
  • Parallel overhead: thread creation, synchronization, communication, load imbalance
Memory Ordering & Memory Barriers
  • CPUs and compilers may reorder instructions for performance — can break concurrent code
  • Memory barrier (fence): instruction that prevents reordering across it
  • volatile in Java: prevents caching + prevents reordering (but not atomicity)
  • happens-before relationship: if A happens-before B, A's effects are visible to B
  • Weak memory models (ARM, POWER) reorder more than x86; need explicit barriers

39 — Virtualization & Docker NEW

Virtualization, Hypervisors & Containers

Running multiple OS environments on one machine — foundational to cloud computing, DevOps, and modern deployment.

Virtualization
  • Technique to run multiple operating systems on a single physical machine simultaneously
  • Each virtual machine (VM) believes it has its own hardware
  • Enables better hardware utilisation, isolation, and easy deployment
  • Foundation of cloud computing (AWS EC2, Google Compute Engine are VMs)
Type 1 Hypervisor (Bare Metal) production
  • Runs directly on hardware — no host OS underneath
  • More efficient and faster — direct hardware access
  • VMs managed by the hypervisor directly
  • Examples: VMware ESXi, Microsoft Hyper-V, KVM (Linux), Xen
  • Used in: data centres, cloud providers (AWS, Azure, GCP)
Type 2 Hypervisor (Hosted) developer use
  • Runs on top of a host OS as an application
  • Simpler to install and use; some performance overhead
  • Examples: VirtualBox, VMware Workstation, Parallels (Mac)
  • Used for: development, testing, running different OS on your laptop

Containers vs Virtual Machines

Containers (Docker) lightweight
  • Containers share the host OS kernel — much lighter than VMs (no separate OS per container)
  • Each container gets isolated: filesystem, processes, network, users (via Linux namespaces + cgroups)
  • Start in milliseconds; use tens of MBs vs GBs for VMs
  • Docker packages app + dependencies into an image — runs the same everywhere
  • Docker image: read-only blueprint. Docker container: running instance of an image
  • Weakness: less isolation than VMs — containers share kernel (kernel vulnerability affects all)

40 — Distributed Systems Basics NEW

Distributed Systems Basics

When multiple computers work together to appear as one system — the foundation of the modern internet.

What is a Distributed System?
  • A collection of independent computers that appear to the user as a single coherent system
  • Computers communicate via a network — no shared memory
  • Goals: resource sharing, fault tolerance, scalability, openness
  • Examples: Google's search infrastructure, Amazon's AWS, BitTorrent, DNS
Key Challenges
  • Partial failures: some nodes fail while others keep running — hard to detect
  • Network partitions: network splits into disconnected groups
  • Latency: network communication is orders of magnitude slower than local memory
  • Clock synchronization: no single global clock — hard to order events
  • Consistency: keeping data the same across all replicas
CAP Theorem must know
  • A distributed system can only guarantee 2 of 3 properties:
  • C — Consistency: every read returns the latest write
  • A — Availability: every request gets a (non-error) response
  • P — Partition Tolerance: system continues operating despite network splits
  • Since network partitions always happen in real systems, you choose: CP (consistent) or AP (available)
  • Example: HBase = CP; Cassandra = AP; RDBMS without replication ≈ CA
Synchronization in Distributed Systems
  • Lamport Timestamps: logical clocks to order events without real-time clocks
  • Mutual exclusion via distributed locks (e.g. Redis SETNX, ZooKeeper)
  • Consensus algorithms: Paxos, Raft — agree on a value among N nodes despite failures
  • Raft is used by etcd (Kubernetes), CockroachDB; Paxos used by Google Chubby
Distributed OS vs Network OS
  • Distributed OS: tightly coupled — OS manages all nodes as one; users don't see individual machines (e.g. Amoeba)
  • Network OS: loosely coupled — each machine has its own OS; users log in to specific machines; share via NFS/SMB
  • Most real-world systems are Network OS style; true Distributed OS is mostly research
Inter-Process Communication (IPC) in Distributed Systems
  • RPC (Remote Procedure Call): call a function on a remote machine as if it's local
  • gRPC: Google's modern RPC framework using Protocol Buffers (used in microservices)
  • Message Queues: async communication — sender puts message in queue; receiver processes when ready (RabbitMQ, Kafka)
  • REST APIs: stateless HTTP communication — most common for web services
  • Shared nothing architecture: each node has its own memory and storage; communicate only via messages
41 — Interview Questions

Hot Interview Questions

The most commonly asked Operating Systems questions — review before every interview.

Q: What is an Operating System and what are its functions?
  • Software that acts as an interface between user and hardware
  • Functions: process management, memory management, file system management, I/O management, security, networking
Q: What is the difference between process and thread?
  • Process: independent program in execution; has its own memory space; isolated; heavy to create
  • Thread: unit of execution within a process; shares process memory; lightweight; crash can affect whole process
Q: What is the difference between User Mode and Kernel Mode?
  • User Mode: restricted — apps run here; cannot directly access hardware; crash affects only that process
  • Kernel Mode: privileged — OS runs here; full hardware access; crash = system crash
  • Transition: system call, interrupt, or exception switches from user → kernel mode
Q: What is the difference between multiprocessing, multitasking, and multithreading?
  • Multiprocessing: multiple CPUs/cores running in true parallel
  • Multitasking: one CPU rapidly switches between tasks (time-slicing)
  • Multithreading: multiple threads within one process running concurrently
  • Multiprogramming: CPU switches between programs only when one is waiting for I/O
Q: What is a deadlock? What are the four necessary conditions?
  • A state where processes are permanently stuck waiting for each other's resources
  • Conditions: Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait
  • All four must hold simultaneously for deadlock to occur
Q: What is the difference between paging and segmentation?
  • Paging: fixed-size pages; OS-level division; no external fragmentation; may have internal fragmentation
  • Segmentation: variable-size logical segments (code, data, stack); programmer view; no internal fragmentation; may have external fragmentation
Q: What is virtual memory and what is a page fault?
  • Virtual memory: technique that uses disk as extension of RAM; programs can be larger than physical RAM
  • Page fault: when a program accesses a page not currently in RAM; OS loads it from disk into a free frame
Q: What is context switching?
  • Process of saving the state of the currently running process (into PCB) and loading the saved state of another process
  • Allows CPU to switch between processes without losing progress
  • Context switching itself is overhead — no useful work is done during the switch
Q: What is the difference between mutex and semaphore?
  • Mutex: binary (0/1); only the thread that locked it can unlock it; strict ownership
  • Semaphore: integer (0 to N); any thread can signal; used for counting resources
  • Use mutex for mutual exclusion; use semaphore for resource counting or signaling
Q: What is thrashing and how do you prevent it?
  • System spends more time swapping pages than doing real work; CPU utilisation plummets
  • Caused by too many processes with too few frames each → constant page faults
  • Prevention: reduce degree of multiprogramming; use working set model to keep active pages in RAM
Q: What is Round Robin scheduling and what is a time quantum?
  • Each process gets a fixed time slice (quantum); after it expires, the process goes to the back of the queue
  • Fair — no starvation; ideal for interactive systems
  • Small quantum → more context switches (overhead); large quantum → behaves like FCFS
Q: What is the difference between monolithic and microkernel?
  • Monolithic: all OS services in kernel space; fast but a bug can crash the system (Linux)
  • Microkernel: only essential services in kernel; rest in user space; more stable and secure but slower (Minix, QNX)
Q: What is a PCB?
  • Process Control Block — data structure the OS maintains for every process
  • Contains: PID, process state, program counter, CPU registers, memory info, I/O status, scheduling info
  • Used during context switching — saved when process is paused, restored when resumed
Q: Explain the Dining Philosophers problem and one solution.
  • 5 philosophers around a table; each needs 2 forks to eat; one fork between each pair
  • If all grab left fork at once → circular wait → deadlock
  • Solution: number the forks; philosophers always grab the lower-numbered fork first — breaks circular wait
Q: What is DMA and why is it important?
  • Direct Memory Access — lets hardware transfer data directly between device and RAM without CPU involvement
  • CPU programs the DMA controller (source, destination, size) and is then free for other work
  • Dramatically improves I/O throughput — critical for disk, network, and GPU transfers
Q: Containers vs Virtual Machines?
  • VMs: full OS isolation, gigabytes in size, minutes to start, strong security boundary
  • Containers: share host OS kernel, megabytes in size, milliseconds to start, weaker isolation
  • Both used together in production: VMs for isolation between tenants; containers for app deployment within a VM
✅ Pro tip: For any OS question about algorithms (scheduling, page replacement, disk scheduling), always mention the tradeoff — no single algorithm is best for all situations. LRU is best in practice for page replacement; Round Robin is best for interactive systems; SCAN/LOOK is best for disk scheduling. Interviewers love candidates who can explain the why.
